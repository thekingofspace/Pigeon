What is Pigeon?

Pigeon is a networking library for Roblox. You give a channel a name, you build that same name on the server and on the client, and the two are talking. Pigeon takes care of the RemoteEvents underneath.

The problem it solves

The normal way to network in Roblox is one RemoteEvent per feature. A shop event, a combat event, a chat event, a quest event. Each one is an Instance you have to create, name, parent, find and wait for.

That works fine for ten features. It stops being fine later:

  • Every feature adds another Instance to ReplicatedStorage.
  • Every client has to WaitForChild each one before it can be used.
  • A message sent before the client is listening is gone for good.
  • Turning a system off means remembering every connection it made.
  • Nothing stops a player firing an event they should not have access to.

Pigeon fixes all five at once. You stop thinking about Instances and start thinking about named channels.

The three things you use

Pigeon has three objects. Most games only ever touch the first one.

Carrier

A carrier is a named channel. It is the thing you send on and listen on. You make one with Pigeon.new("Shop"). Everything you do day to day is a method on a carrier: On, Emit, Broadcast, Call, rooms, guards and middleware.

Read more in Carriers.

Transformer

A transformer decides which RemoteEvent a carrier's traffic rides on. Every carrier makes one from its own name, so you never have to think about it. You only reach for one directly when you want a group of channels to share a remote, or when you want to shut a group of channels down in one call.

Read more in Transformers.

Staged table

A staged table is a normal table whose changes replicate. Write to it on the server and every client holding it sees the write. There is no sync code to write and nothing to compare.

Read more in Staged Tables.

How a message travels

This is the whole path a fire and forget message takes. You only write the first line and the last line.

Server to client

shop:Broadcast("Sold", id) → guard check → middleware
→ pick the remote → send now, or queue it
→ middleware → your On("Sold") handler

Each step is a feature you would otherwise have to build:

StepWhat it does
Guard check Drops players who have not passed the channel's handshake. See Handshakes.
Middleware Lets you log or rewrite the message, and turn one away by renaming it to an event nothing listens for. See Middleware.
Pick the remote Hashes the channel onto one of the pooled RemoteEvents. See The Ref Pool.
Send now, or queue Holds the message if the client has not called Init yet. See Startup and Buffering.

A complete example

Here is a working shop channel. Nothing has been left out.

Server 
local ReplicatedStorage = game:GetService("ReplicatedStorage")
local Pigeon = require(ReplicatedStorage.Pigeon)

local shop = Pigeon.new("Shop")

-- The client can ask to buy something. Whatever you return goes back to them.
shop:On("Buy", function(player, itemId)
	if not canAfford(player, itemId) then
		return false, "too expensive"
	end
	giveItem(player, itemId)
	return true
end)

-- Tell everyone the stock changed.
shop:Broadcast("StockChanged", getStock())
Client 
local ReplicatedStorage = game:GetService("ReplicatedStorage")
local Pigeon = require(ReplicatedStorage.Pigeon)

local shop = Pigeon.new("Shop")

shop:On("StockChanged", function(stock)
	updateShopUi(stock)
end)

-- Handlers are set up, so let the server start sending.
shop:Init()

local ok, reason = shop:Call("Buy", "sword")
if not ok then
	print("could not buy:", reason)
end

Note

Server handlers get the player as the first argument. Client handlers do not, because there is only one sender.
